Lesson 3 · Agentic generation for the Teaching Assistant

When the agent owns memory: harness, session, memory

New assumptions: the agent may write memory, and Postgres keeps only what is needed to run the agents. This lesson shows what still has to stay in Postgres, where a Thread lives now, and where Google's Memory Bank fits. About 15 minutes.

Warm-up: from memory, why did Lesson 1 recommend one agent session per job?

Generators never wrote memory, Postgres was the only source of truth, and no platform could reliably keep a session through an overnight Reaction. The first two premises are now withdrawn, and the third turned out to be wrong for ADK (see below). So the rule is open again.

What changed

  • Agents may write memory. This reverses "generators never write memory" from ticket 07.
  • Thread history may leave your schema. Postgres keeps only the harness: what your own code needs to run the agents.
  • Correction to Lessons 1–2. The ADK docs list only an in-memory session service for TypeScript, but the published @google/adk 2.1.0 package includes DatabaseSessionService, which accepts postgres:// URIs, plus VertexAiSessionService and VertexAiMemoryBankService.[1] An ADK session can therefore live durably in your Supabase Postgres.

The harness test. Keep a fact in Postgres if your code needs it deterministically: to route a Telegram update, draw the right buttons, deduplicate, schedule, cap spend, or choose which Thread to start. A model's memory is probabilistic and eventually consistent. Button rows and idempotency can't depend on it.

For this bot the harness is roughly: Telegram message_id ↔ Thread/session and message kind (so a reply or a button tap finds its target), the Topic's latest Lesson (only its Simple/Proceed/Difficult taps take effect; a tap on an older Lesson gets a toast), update_id deduplication, jobs and runRefs, the published Backlog copy, which Topic is in progress (and whether it is finished or paused), and the usage and spend log. Everything else is a candidate to move.

A Thread can now be one session

/next → create session→ Lesson→ tap / Reply = new event→ idle for hours, nothing running→ tap = new event→ /next → newer Thread; this session stays resumable

The Thread is the session. A Reaction or Reply is appended as a new event and runs one turn, and nothing runs in between. The overnight gap is harmless because the session is stored, not held in a running process. Threads are never closed (ticket 12, 2026-09-17): older Threads still accept Replies, so a session must stay resumable indefinitely, and there is no "close" moment for writing memory. Write memories incrementally instead: after each turn from that turn's events (the quickstart recommends add_events_to_memory for incremental processing), or when a newer Thread starts. Two Lessons may be generated at once, but they belong to different sessions, and the Topic level stays a harness rule, so concurrent turns don't conflict.

One cost to watch with session-per-Thread: the context grows with each turn, and every turn re-sends it. That is fine for a Thread of a few Lessons. Keep Threads short, and let /next start fresh.

Your question: is Memory Bank relevant?

Yes. It is the managed form of the "agent writes memory" layer. What it does, per Google's docs:[5]

  • It extracts and consolidates memories from session events. New facts are merged into existing memories rather than appended, and you can steer extraction with custom topics and few-shot examples.
  • It retrieves by similarity within a scope. The ADK quickstart uses {user_id, app_name}.[6]
  • It keeps revisions and supports TTL, so you can see how a memory changed, and stale memories expire.
  • It accepts direct writes (CreateMemory) and event ingestion. A classified Note could be written directly instead of being extracted.
  • ADK integration: PreloadMemoryTool loads memories every turn. LoadMemoryTool loads them when the model decides to, and a callback's add_session_to_memory() writes them. The agent can run on Cloud Run (--memory_service_uri=agentengine://ID). The quickstart shows only Python, but the TS package ships the service class.

What it costs you

  • Money: storage at $0.30/GiB-month, and $0.085 per 3M reads or per 1M writes, billed since 2026-09-01. Gemini tokens for extraction and embeddings are billed separately.[7] For one learner that comes to cents.
  • Setup: a GCP project with billing, and an Agent Platform (Agent Engine) instance whose id scopes the memories, even if the agent itself runs elsewhere.
  • Your rules: extraction runs on Google's model, so OpenRouter-only no longer covers memory. Consolidation is non-deterministic, so "Answer outcomes never move the level" has to stay a harness rule in your code. Google also warns about memory poisoning, where false facts get stored. A learner's Reply is untrusted input.

Practice: which layer?

1. The Telegram message_id of the Topic's latest Lesson, so a Simple/Proceed/Difficult tap is either applied or answered with a toast.

2. The full text of the Thread's three Lessons and the learner's Instruction, needed for the next Follow-up.

3. "Struggles with idempotency; an analogy to insurance claims numbers helped", learned across several Threads.

4. Which Topic is in progress, so the 07:00 run knows what to start.

5. A pending Lesson generation's runRef and attempt count.
